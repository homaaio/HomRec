[Version 2.3] - 2026-09-19 (unreleased)

  Fixed / improved:
  - hr_pipeline.cpp: pipe_handle/recording are std::atomic (UI vs capture/writer thread data race).
  - hr_pipeline.cpp: catch-up frames are converted once and written N times (QueuedFrame::repeat) instead of re-converted up to 90x.
  - hr_pipeline.cpp: an evicted (dropped) frame passes its timeline slots to the next one - fixes audio lagging behind video after "Recording overloaded: dropping frames".
  - hr_pipeline.cpp / recording_controller: bounds-checked, change-aware preview fetch (hr_pl_get_preview_ex); closes a possible heap overflow.
  - main_frame.cpp: preview repaints only on new frames; no per-paint snapshot copy; debounced overlay autosave; stuck-drag recovery; fewer idle relayouts.
  - hr_audio.cpp: replay ring buffer trims in 1s chunks; WAV files written outside the audio mutex.
  - hr_update.cpp: HTTPS-only, truncated/corrupt downloads rejected, version tag sanitised.
  - hr_archive.cpp: PowerShell fallback works with spaces in paths; 2-minute timeout.
  - console_window.cpp: `rm @homrec` script is UTF-8, waits on our PID, refuses root-like folders.
  - hrc_config.cpp: settings/overlays saved atomically (temp file + replace).
  - Removed stale duplicate src/hr_ffmpeg_runner.cpp (build uses ffmpeg/hr_ffmpeg_runner.cpp).
  
[Version 2.2.1] - 2026-09-19

- Fixed: overlays couldn't be moved/resized on the preview - no frame ever
  showed up and clicking did nothing, leaving "Position Overlays..." as the
  only way. The preview now draws a labelled frame (with corner handles)
  around every overlay, a clicked overlay stays selected and highlighted
  after releasing the mouse, the cursor changes over grabbable frames/
  handles, and the arrow keys nudge the selected overlay (Shift = 10px).
  Frames are now mapped through the pipeline's real composite size instead
  of the full monitor size, so they line up in window-capture mode too.
- Fixed: with "Disable live preview" on, clicking the preview did nothing.
  It now takes a screenshot and lets overlays be edited on it right in the
  preview (right-click: Refresh screenshot / Done editing, or Esc). This
  also works while a recording or Instant Replay is running, and no longer
  risks tearing down the pipeline Instant Replay is using when it ends.
- Fixed: ugly black borders/box on the whole recording when a game runs
  exclusive fullscreen at a different resolution than the desktop (e.g.
  1366x768 on a 1600x900 desktop) - a previous fix for the same mismatch
  (see 2.2.1's "diagonal line/pixel corruption" entry below) plugged the
  corruption by pinning dx_capture()'s output to the size the recording
  buffer/ffmpeg pipe expect, but did it by black-letterboxing whatever
  didn't fit - correct for a one-tick glitch, but a permanent eyesore for
  a game that runs its whole session at the mismatched resolution.
  hr_dx_capture() (hr_dxgi_capture.cpp) now nearest-neighbour stretches
  the real captured frame to fill the pinned output shape instead, so the
  recording always uses the full frame - visually indistinguishable from
  native capture for near-identical aspect ratios like this one.
- Fixed: recordings had a constant ~0.5-0.8s audio lag on every session.
  hr_merge_av() (hr_tools.cpp) muxed the finished video and the captured
  audio WAV assuming both start at the same real-world instant, but
  video's "frame 0" and audio's "sample 0" are set several setup steps
  apart in RecordingController::Start() (ffmpeg process spawn, DXGI
  device/duplication creation, etc. all happen in between) with nothing
  measuring or compensating for that gap. Start() now measures the actual
  gap (av_start_skew_sec_, logged) between the pipe being pointed at the
  output file and hr_audio_reset_buffers() marking audio's zero-point, and
  hr_merge_av() applies it as an -itsoffset (or -ss trim, if the gap runs
  the other way) on the audio input so the two line back up.
- Fixed: window-capture recordings (e.g. recording just the Garry's Mod
  window) came out as skewed, streaky, garbled video. capture_loop()
  (hr_pipeline.cpp) cropped the window rect by compacting bgra_buf IN
  PLACE. Any tick that didn't get a fresh DXGI frame (the very first call
  always, plus every HR_DX_TIMEOUT / HR_DX_LOST tick) deliberately
  re-encodes "whatever is still in bgra_buf" - which was now the already
  cropped, tightly-packed data - and cropped it AGAIN using the full-
  monitor row stride, shearing the picture more each time. bgra_buf now
  always stays the pristine full-desktop frame; the crop goes into a
  separate work_buf. Overlays and the cursor are also drawn on a work
  copy now instead of on bgra_buf itself, so repeated ticks no longer
  stack overlays/cursor on top of themselves (ghost trails, alpha overlays
  getting darker) either. The live preview reads the same per-tick frame.
- Fixed: app crashed (silent std::terminate) on the SECOND Stop of a
  session. RecordingController::StopAsync() assigned a new std::thread to
  finalize_thread_ without joining the previous recording's (already
  finished, but never joined - the UI uses StopAsync, only the blocking
  Stop() joined) thread; assigning to a joinable std::thread terminates
  the process. StopAsync() and Start() now join it first, and Start()
  refuses (with a message) while a previous recording is still being saved.
- Fixed: possible out-of-bounds read / crash when a running preview
  pipeline was re-targeted at a different window (crop rect changed by
  the UI thread while capture_loop() was mid-frame and reading the four
  crop_* fields separately). The rect is now guarded by crop_mtx,
  snapshotted once per frame and re-validated against the real frame size.
- Fixed: a timed-out hr_pl_end_recording_segment() left its close request
  armed, so the writer thread could close the NEXT recording's pipe (early
  EOF to ffmpeg) as soon as its queue ran empty. Cleared on timeout and
  whenever hr_pl_set_recording() (re)activates a pipe.
- Fixed: hr_dxgi_capture.cpp's Map() wait deadline was stored in a DWORD
  while GetTickCount64() is 64-bit, so after ~49.7 days of PC uptime every
  read-back timed out instantly (frozen/duplicated frames). Now ULONGLONG.
- Fixed: recorded audio ending up noticeably (often 15-20s) "behind" the
  video on playback. RecordingController::Start() (recording_controller.cpp)
  used to call hr_audio_reset_buffers() - the call that actually starts
  accumulating this recording's audio - *before* the capture pipeline was
  even created/started, i.e. before hr_pl_create()'s D3D11 device + DXGI
  duplication setup (including its own up-to-40x50ms retry loop when the
  desktop isn't immediately duplicable: a UAC prompt, a fullscreen game
  holding exclusive access, a driver still waking up, etc.) and before
  hr_pl_start() had produced a single real video frame. hr_merge_av()
  (hr_tools.cpp) lines the resulting audio track up starting at t=0
  against the video track's own frame 0 with no compensating offset, so
  audio's t=0 being consistently earlier in real time than video's t=0
  meant the audio matching any given on-screen moment played out later
  than that moment was shown - "the sound lags the picture." Moved the
  hr_audio_reset_buffers()/hr_audio_set_volumes() call to right after the
  pipeline is confirmed started and flipped into recording mode instead,
  as close as this function can get audio's start to video's actual first
  frame.
- Fixed: recording could measurably drop game framerate (e.g. Minecraft)
  more than it needed to, worst on 4-6 core machines. Two contributing
  issues in hr_pipeline.cpp:
    1. Yuv420pWorkerPool::EnsureStarted() sized its thread pool as
       min(hardware_concurrency() - 1, 4) bands, which only ever held back
       a single core "for the capture thread ... and everything else" -
       despite that same comment's own wording ("holding a couple back").
       On a quad-core machine that put 75% of all cores into color
       conversion alone (67% on a hexa-core), on top of the separately-
       boosted capture/writer threads, starving the actual game of CPU for
       the whole recording. Now reserves 2 cores before splitting into
       bands (still capped at 4 bands total, so 8+ core machines are
       unaffected).
    2. writer_loop() set THREAD_PRIORITY_HIGHEST unconditionally, once, on
       thread start - unlike capture_loop(), which already modulates
       between HIGHEST and ABOVE_NORMAL based on boost_priority (see that
       flag's own comment: it exists specifically so a passive feature
       like Instant Replay's background buffer doesn't run at a
       system-wide-contending priority indefinitely just for sitting
       there unnoticed). Instant Replay's background segment writer keeps
       this thread genuinely busy the entire time a game is running, so it
       was paying that same cost the capture-thread fix was supposed to
       have already removed. writer_loop() now checks boost_priority the
       same way capture_loop() does, both at thread start and on every
       loop iteration (since boost_priority can flip without the writer
       thread restarting).

[Version 2.2.0] - 2026-09-17 (stable)

- Fixed: recording still ran the live-preview thumbnail generator at up
  to "Preview FPS" (Settings > General, 60 by default) times a second
  even with Settings > "Disable live preview (for performance)" checked
  - the exact CPU cost that setting exists to remove, still being paid
  in full. A manual recording always keeps a real Pipeline object alive
  (hr_pipeline.cpp) regardless of this setting, since it's also the
  encoder path - so the setting couldn't be implemented by simply not
  creating one. But capture_loop() had no way to know the thumbnail it
  was building every tick (a full box-filter downscale of the captured
  frame, not a cheap operation) had nowhere to go: PreviewPanel::OnPaint()
  already skips reading it whenever disable_preview is set (it just
  draws the ":)" placeholder instead), so every one of those thumbnails
  was pure waste. Added Pipeline::preview_needed (hr_pipeline.cpp) plus
  hr_pl_set_preview_needed(), and wired RecordingController to push it
  from state_.disable_preview at every point a pipeline is created *or*
  reused (Start(), EnableInstantReplay(), EnsurePreview(), and
  RefreshPreviewSettings() - the last one specifically covers flipping
  the checkbox mid-recording, where the existing pipeline has to be
  reached directly rather than only affecting the next preview-only
  pipeline EnsurePreview() would create). capture_loop() now skips
  update_preview() entirely when the flag is off. This is a real,
  continuous CPU cut during every recording made with the setting on -
  the reason it exists in the first place ("weak devices").
  Investigated but did NOT find a memory leak to go with it: audited
  pipe_queue/free_bufs (hr_pipeline.cpp) and the overlay compositor's
  per-type caches (hr_overlay_render.cpp) - all are properly bounded
  (MAX_QUEUE_SIZE/MAX_FREE_BUFS, and PruneStaleCaches() on every overlay
  count change) and none grow unbounded. The one bug that *did* match
  "memory climbs during recording, only partly comes back after Stop"
  (pipe_queue bypassing its own cap during a catch-up burst) was already
  fixed in an earlier beta - see hr_pipeline.cpp's own "BUGFIX (freeze +
  memory growth after Stop..." comment a few lines above where this
  round's fix landed. The ~100-150MB a recording session settles at
  going forward looks like ordinary buffer overhead for this
  resolution/overlay setup (capture buffer, scaled/YUV working buffers,
  the wx UI itself) rather than a leak, and ffmpeg's own memory is a
  separate process not even counted in that figure (see hr_pc_log.cpp -
  it reads GetProcessMemoryInfo() on hr.exe's own process handle only).

- Added: File menu now has "Open Program Files" (opens the folder hr.exe
  itself lives in - ffmpeg/, plugins/, icons/, logs/, homrec.hrc - as
  distinct from the existing "Open Recordings Folder," which opens
  wherever Settings > Output folder points, often a completely different
  place) and "Import Plugin (.hrp)..." (file picker -> copies the chosen
  .hrp into plugins/ next to hr.exe, same as the README's documented
  "download it and drop it into plugins/" step, then calls
  LuaPluginEngine::LoadPluginArchive() on it immediately instead of
  requiring a restart - LoadAll() already extracts/loads any *.hrp
  sitting in plugins/ the same way on every future launch, so this is
  just doing that copy-and-load through a dialog instead of a file
  manager). main_frame.h/.cpp, language.cpp (new "open_program_files"/
  "import_hrp" keys, English defaults + required-key list so a custom
  .hrl without them still falls back cleanly instead of showing a blank
  label).

- Version bump only, no functional/behavior change:
  HR_APP_VERSION 2.2-b.4 -> 2.2.0. This is the first release this round
  actually calls "stable" rather than a numbered beta - see 2.2-b.4's
  own changelog note below about the beta-numbering scheme this
  supersedes.

[Version 2.2-b.4] - 2026-09-17

Note on the version number: HR_APP_VERSION (src/ui/version.h) had stayed at
a flat "2.2.0" through the entire beta/beta2/.../beta5 cycle above - it was
never actually bumped per beta despite the changelog tracking each one by
name. This release is the first to put a real, distinct string into
HR_APP_VERSION (previously it was always the same "2.2.0" no matter which
beta was actually running). It lands as "2.2-b.4" per this round's
instructions rather than continuing on from "beta5" above; whoever cuts
the next release should decide whether that continues this "-b.N" scheme
going forward (e.g. "2.2-b.5" next) or jumps back in line with the
changelog's own beta numbering - just flagging that the two numbering
tracks aren't currently in sync so it doesn't look like a version regression.

- Fixed: hr_version_string() (src/hr_app_logic.cpp) always returned a
  hardcoded "1.6.2", completely disconnected from HR_APP_VERSION and
  stale since long before the 2.2 betas - despite version.h's own header
  comment already claiming hr_version_string()/hr_version_gt() "build off
  HR_APP_VERSION now". CURRENT_VERSION now is HR_APP_VERSION (added the
  `#include "ui/version.h"`) instead of a second hand-maintained literal.
- Fixed: hr_ff_destroy() (ffmpeg process manager) still unconditionally
  closed ctx->hStdin when force-killing a still-running process, in both
  pipe_input and non-pipe_input mode. In pipe_input mode that handle is
  the same raw-video pipe the capture pipeline's writer thread owns and
  closes itself exactly once, right after its loop ends (see
  writer_loop() in hr_pipeline.cpp) - this is the exact same
  handle-ownership race hr_ff_kill() and hr_ff_stop_graceful() were
  already fixed for elsewhere in this same file, just missed here.
  RecordingController::StopFinalizeTail()'s ~30s last-resort force-stop
  path calls hr_ff_destroy() directly on a still-running ctx, which is
  precisely the case where the writer thread can still be mid-WriteFile()
  on that handle from another thread. Now only non-pipe_input mode (where
  stdin is solely ffmpeg's own interactive channel) closes the handle
  here directly; pipe_input mode just drops the reference, same as the
  other two functions.
- Reorganized: ffmpeg-related code and the ffmpeg binary itself now live
  under a new ffmpeg/ folder at the repo root instead of being split
  between src/ (hr_ffmpeg_runner.cpp) and the bare repo root
  (ffmpeg.exe). ffmpeg/hr_ffmpeg_runner.cpp is unchanged apart from the
  fix above; it's still compiled straight into hr.exe (no new DLL/build
  target - Makefile and CMakeLists.txt both just point at the new path).
  hr_find_ffmpeg() (src/hr_app_logic.cpp) now checks <exe_dir>/ffmpeg/
  first, still falling back to <exe_dir> itself, cwd, then PATH, so older
  portable installs that had ffmpeg.exe sitting loose next to hr.exe keep
  working. installer/HomRec.iss now packages ffmpeg\ffmpeg.exe into
  {app}\ffmpeg instead of {app} directly, and tools/homrec_build.py's
  find_ffmpeg()/collect_files() look for and package it from ffmpeg/ the
  same way (falling back to the old repo-root ffmpeg.exe location if
  that's still where it's sitting locally). Did not go further and add a
  separate ffmpeg/include/ - hr_ffmpeg_runner.cpp has never had its own
  header (every caller just declares the handful of extern "C" hr_ff_*()
  functions it needs inline, same as hr_pipeline.cpp already does for
  hr_dx_*/hr_sw_*), and nothing else in this codebase keeps headers in a
  separate include/ tree away from their .cpp, so there's nothing for an
  include/ folder to hold yet. ffmpeg.exe itself is still not checked
  into the repo (third-party binary) - see the new ffmpeg/README.md.
- Fixed: installer/HomRec.iss's file-association task has referenced
  icons\files_icons\hrc.ico / hrp.ico (and SetupIconFile has referenced
  icons\hrsetup.ico) since the feature was added several betas ago, but
  none of those three files actually existed anywhere in the repo -
  icons/files_icons/ didn't even exist as a folder. Because every one of
  those [Files]/[Icons] entries is flagged skipifsourcedoesntexist, ISCC
  would happily build a "successful" installer that silently shipped
  with no .hrc/.hrp file-type icons and reused hr.exe's own main.ico for
  Setup.exe instead of a dedicated one - never an error, just quietly not
  doing what the script (and installer/README.md) both claim it does.
  Added icons/files_icons/hrc.ico and hrp.ico (simple flat file-badge
  icons, blue/green, labelled HRC/HRP) and icons/hrsetup.ico (a
  distinct install-themed icon - box + arrow - instead of another copy
  of main.ico) so the installer actually has real assets to package.

[Version 2.2 beta5] - 2026-09-16

- Fixed: adding a custom hotkey (Settings > Hotkeys > "+ Add Hotkey", or
  just opening that tab with any custom hotkeys already saved) popped a
  "wxWidgets Debug Alert" dialog every time. Cause: AddCustomHotkeyRow()
  (settings_dialog.cpp) added its action-text field to a
  wxBoxSizer(wxHORIZONTAL) row with `wxEXPAND | wxALIGN_CENTRE_VERTICAL`
  - wxBoxSizer::DoInsert() asserts (debug builds only) on wxEXPAND
  combined with any alignment flag, since wxEXPAND already fills that
  cell and the alignment flag is a no-op at best. Dropped the redundant
  wxALIGN_CENTRE_VERTICAL; layout is unchanged since wxEXPAND already did
  the job. Checked the rest of the codebase for the same pattern - this
  was the only instance.
- Fixed: the hotkey "Bind"/capture button (the (none)/F9/etc. box you
  click then press a key into - HotkeyButton, themed_widgets.h/.cpp) was
  almost invisibly small on the custom-hotkey rows, making it hard to
  even click to start capture. Cause: HotkeyButton is a bare wxPanel that
  draws itself (no child sizer of its own) and never overrode its best
  size, so any sizer cell that doesn't force a size onto it directly
  (proportion 0, no wxEXPAND - which is how AddCustomHotkeyRow() adds it,
  unlike the four fixed hotkeys' growable-column grid) collapsed it down
  to whatever the platform's bare-minimum panel size is. Added
  HotkeyButton::DoGetBestSize(), sized off a realistic combo string
  ("Control+Shift+PageDown") with a floor under both dimensions, so it's
  a sensible clickable size everywhere it's used.
- Hardened HomRecMainFrame::OnClose() against closing via Alt+F4
  specifically crashing. Alt+F4 is a system accelerator Windows can
  re-deliver as a second WM_CLOSE while the first is still unwinding
  (Destroy() only *schedules* the real destruction, same "several
  event-loop turns later" gap as the g_frame race fixed in beta4 below) -
  a second entry to OnClose() would re-run every teardown step
  (hr_hk_stop/hr_hk_destroy on an already-torn-down hotkey handle,
  tray_icon_ cleanup, etc.) a second time. Added an IsBeingDeleted()
  guard at the top of OnClose() - wx's own idempotency flag for this,
  set synchronously by Destroy() before the object is actually freed -
  so a re-entrant close bails out instead of repeating the teardown.
  Investigated but could not fully confirm against a real crash log:
  logs.7z couldn't be opened in this environment (no 7z/p7zip available
  and no network access to install one), so this fix is based on static
  review of the shutdown path, not a captured stack trace. Everything
  else checked there (RecordingController's destructor thread-joins, the
  update-check thread, the hotkey thunks) already looked correctly
  guarded. If this crash recurs, a plain-text crash log/dump (not .7z)
  would help pin down the exact stack.

[Version 2.2 beta4] - 2026-09-16

- Fixed: a recording almost always took ~20-30s to "save" after pressing
  Stop, and the resulting file was frequently corrupt/unplayable -
  reported as "a 10 second recording saves in about 20 seconds." Root
  cause: StopAsync() deliberately keeps the capture pipeline's writer
  thread alive after Stop() when live preview is left on (the default),
  so the preview keeps working instead of going dark - but the writer
  thread is also the only thing allowed to close ffmpeg's stdin pipe
  (hr_ff_stop_graceful() doesn't, by design - see its own comment), and
  it only ever did that as part of its own full shutdown, which this
  path intentionally skips. So ffmpeg sat blocked reading pipe:0,
  StopFinalizeTail()'s hr_ff_wait() (3s/10s/30s budget) could never see
  the EOF it needed and always ran out its full timeout, and the file
  got TerminateProcess()'d mid-write instead of finalized. This wasn't
  occasional/under-load behavior - it happened on every single Stop with
  preview enabled. Added hr_pl_end_recording_segment() (hr_pipeline.cpp):
  asks the writer thread to close whatever pipe it currently holds once
  its queue drains, without stopping the thread or the pipeline, and
  blocks the caller briefly for confirmation. StopAsync() now calls this
  before waiting on ffmpeg instead of skipping straight to the wait.
- Fixed: Instant Replay's segment writer logged "didn't finish
  gracefully in time - killing it" on essentially every handoff (pausing
  for a manual recording, "Save Replay," turning the feature off) instead
  of only under genuine load, and the segment being closed at that moment
  came out truncated/corrupt. Same root cause as above - the segment
  writer's ffmpeg shares the same pipeline_/pipe_handle as everything
  else this class does with it, and nothing was ever closing that pipe
  on a segment handoff either. StopInstantReplayEncoder() and
  StopInstantReplayEncoderAsync() now both call
  hr_pl_end_recording_segment() before stopping/waiting on that segment's
  ffmpeg process.
- Fixed: a crash ("unhandled C++ exception / std::terminate()") that
  could occur about a second after the "Instant Replay: segment writer
  didn't finish gracefully in time - killing it" warning.
  StopInstantReplayEncoderAsync() runs its stop/wait/kill/destroy
  sequence on a bare std::thread with no exception handler anywhere
  above it on the call stack - every other bare-thread lambda in this
  codebase (Pipeline::capture_loop()/writer_loop()) was already wrapped
  in a try/catch specifically because an uncaught throw there calls
  std::terminate() and takes the whole app down; this one thread was
  missed. Wrapped it the same way.
- Fixed (found while fixing the above): StopInstantReplayEncoderAsync()'s
  background thread now also has to call hr_pl_end_recording_segment(),
  which touches the pipeline_ pointer - but that thread used to be fully
  detached, and Start()/EnableInstantReplay() can destroy and replace
  pipeline_ (a fresh hr_pl_create()) almost immediately after pausing
  Instant Replay if the capture size or monitor changed, racing the
  detached thread's use of the now-freed pointer. Changed the thread to
  be tracked (instant_replay_stop_thread_) instead of detached, same
  pattern preview_teardown_thread_/JoinPendingPreviewTeardown() already
  use for the analogous DXGI-duplication-handle race; added
  JoinPendingInstantReplayStop(), called at every point pipeline_ is
  about to be destroyed/replaced and in the destructor.

  Investigated but NOT changed: high idle/AFK CPU and memory use (~15MB /
  5-8%) with preview and the audio mixer both off. This traces to Instant
  Replay's background buffer actually being on (EnableInstantReplay()) -
  it's a real, continuous rolling recording (full capture rate + live
  encode to disk), which is inherently more expensive than idle preview
  regardless of the preview/audio-mixer settings; those two are unrelated
  knobs. This isn't a discrete bug the way the three fixes above were, so
  it wasn't touched this round - happy to look at cheaper ways to run
  Instant Replay (e.g. a lower dedicated buffer fps/quality separate from
  manual-recording settings) as a followup if that's wanted.

[Version 2.2 beta3] - 2026-09-15
  RecordingController::StopAsync() exists specifically so the Stop
  button doesn't have to block the UI thread, but it still called
  hr_pl_stop() directly - which waits (with a timeout) for the capture
  thread and then the writer thread to each confirm they've actually
  stopped, up to ~1s per thread by design - before ever spawning the
  background finalize thread. Every one of those waits was still
  happening synchronously on the UI thread. Moved hr_pl_stop() inside
  finalize_thread_, alongside the rest of the already-async finalize
  work.
- Fixed: the live preview would freeze for up to 3 seconds right after
  clicking Start, if Instant Replay's background buffer happened to be
  running. Start() paused it by calling StopInstantReplayEncoder(),
  which does hr_ff_wait(replay_ff_, 3000) - a synchronous wait, on the
  UI thread, for the segment writer to finish gracefully. Added
  StopInstantReplayEncoderAsync(), which hands the same stop/wait/kill/
  destroy sequence off to a detached background thread instead; Start()
  now uses that. Losing at most a fraction of a second off Instant
  Replay's last in-progress segment is a fine trade for not freezing
  the UI on every single recording.
- Fixed: turning off (hiding) a webcam overlay didn't release the
  actual camera device - the LED stayed on and other apps still saw it
  as "in use" for as long as the app was running, however long the
  overlay stayed hidden. OverlayCompositor::Apply() skipped hidden
  overlays entirely, so their cache entry (and the HrWebcamCapture
  inside it - a live background thread plus an open Media Foundation
  device handle) never got released the way an actual device change or
  overlay deletion already did. Hidden webcam overlays now have their
  cache entry released immediately; it reopens lazily and cheaply if
  the overlay is shown again.
- Fixed: Instant Replay's "Save Replay" clips came out with no audio at
  all, regardless of mic/system-audio settings - the segment writer
  only ever piped raw video. From the outside this looked the same as
  "video and audio saved separately," since the actual manual-recording
  Stop() path (mic+sys WAV -> mix -> hr_merge_av) was already working
  correctly and had nothing wrong with it. Added a rolling audio buffer
  (hr_audio_set_max_buffer_sec()/hr_audio_snapshot_to_wav() in
  hr_audio.cpp) that runs only while Instant Replay's background buffer
  is active with no manual recording in progress, and wired SaveReplay()
  to snapshot/mix/merge it into the saved clip via the same hr_merge_av()
  path manual recordings use - non-destructively, so the rolling window
  keeps accumulating for the next Save Replay instead of being reset to
  empty. A manual Start() explicitly resets the cap back to "unlimited"
  first, so this can't ever truncate an actual recording's audio.
- Fixed: the capture thread ran at THREAD_PRIORITY_HIGHEST any time
  Instant Replay's background buffer was on, even with no manual
  recording running - because that also flips the same internal
  `recording` flag a real recording does. A feature explicitly meant to
  sit in the background unnoticed was, in practice, running at an
  elevated, system-wide-contending thread priority indefinitely for as
  long as the app was open, which is a very plausible source of "the PC
  is loud" on anything with a small cooler (laptops especially).
  Decoupled thread-priority boosting from the `recording` flag into its
  own boost_priority flag (hr_pl_set_priority_boost() in
  hr_pipeline.cpp), set only while a manual recording (or a replay

  had a hardcoded height range of 168–300, which wasn't enough to fit 
  the entire two-paragraph text—without the DT_NOCLIP flag, DrawTextW simply
  clips whatever extends beyond the rectangle's boundaries (#5)

  file (just the ftyp/moov header, nothing playable). Root cause: the
  raw video pipe to ffmpeg shares its OS handle with ffmpeg's stdin, and
  the graceful-stop path (hr_ff_stop_graceful() in
  hr_ffmpeg_runner.cpp) closed that handle itself the instant Stop was
  pressed - including while the writer thread could still be detached
  and mid-write, draining a queued frame backlog in the background (see
  hr_pl_stop()'s handed-off path). That truncated the raw video stream
  and sent ffmpeg an early EOF before more than a few frames had gone
  out. In pipe-input mode, closing this handle is now solely the writer
  thread's job, done exactly once right after its loop actually ends
  (hr_pipeline.cpp); the stop path just drops its own reference instead
  of touching the handle. Non-pipe-input mode (stdin as ffmpeg's real
  interactive control channel) is unaffected and still gets the "q\n"
  graceful-stop keystroke.
- Fixed: on an overloaded machine (e.g. recording heavy screen content
  like a video playing back), the finished recording could come out
  drastically sped up with most of the audio missing - a 16-second
  recording could turn into a ~1-second, tiny (~100KB) file. Root cause:
  frames are piped to ffmpeg with a fixed nominal framerate and no real
  per-frame timestamps, so when the writer/encoder falls behind and
  hr_pipeline.cpp's pipe_queue backpressure drops more frames than it
  can duplicate to compensate, the encoded video.mp4's real duration
  silently shrinks to (frames actually written / nominal fps) - which
  can be a small fraction of how long the recording actually ran. The
  final merge step (hr_merge_av in hr_tools.cpp) then used a flat
  "-shortest", which cut the accurate, wall-clock-captured audio down
  to match that broken short video instead of fixing the real problem.
  Now hr_merge_av() compares the video's own encoded duration against
  the real elapsed recording time (passed in by
  RecordingController::StopFinalizeTail()) and, if the video is
  significantly shorter, re-encodes it with a "setpts" filter to
  stretch it back to real speed before merging - so the output plays at
  the correct speed with the full audio intact instead of losing audio
  to a "-shortest" trim. A normal recording (no such gap) still takes

- Build: src/hr_hotkey.cpp used std::vector (for the new Custom Hotkeys

  further errors right behind it). Added the missing #include <vector>.
- Recordings could finish several times shorter than the actual time
  spent recording (e.g. a 44s take saved as an 11s file) on hardware too
  weak to sustain the requested resolution/fps. The pipeline's rawvideo
  pipe to ffmpeg has no per-frame timestamps - the muxed duration is
  just frame_count/declared_fps - and the existing catch-up mechanism
  meant to compensate for a falling-behind encoder was defeated by the
  same MAX_QUEUE_SIZE backpressure it was supposed to work around: its
  duplicate "catch-up" frames got evicted from the queue just as fast as
  the live ones whenever the writer genuinely couldn't keep up, so they
  never actually reached ffmpeg. Catch-up reps now bypass that backpressure
  cap instead of being dropped, so a chronically overloaded recording
  takes longer to finalize after Stop rather than silently losing
  timeline length.
- h264_amf recordings could come out visibly washed-out/faded compared
  to the same recording with libx264. The app's own BGRA->YUV conversion
  (hr_encoder_helpers.c) produces full-range (PC, 0-255) BT.601 data, but
  nothing ever told ffmpeg/the encoder that, so decoders had to guess -
  libx264's output happened to look right by luck of default player
  behavior, but h264_amf's own range signaling made the mismatch visible.

  -color_trc smpte170m" so both encoders are told the truth instead of
  guessing.
- FFmpeg could fail to launch with a bare "Failed to start the ffmpeg
  process" and no further explanation, on machines where the ffmpeg
  path, output path, or a Windows username anywhere in those paths
  contained non-ASCII characters. _build_cmdline() in
  hr_ffmpeg_runner.cpp converted those std::string (UTF-8) args to
  std::wstring with a plain std::wstring(s.begin(), s.end()), which
  widens each byte 1:1 instead of decoding UTF-8 - correct only for
  pure ASCII input. Any multi-byte UTF-8 sequence came out as garbled
  wide characters, so CreateProcessW either couldn't find the exe or
  choked on a corrupted command line and failed outright.

  MultiByteToWideChar(CP_UTF8, ...), matching the conversion already
  used everywhere else in the app (see hr_app_logic.cpp's
  WideCharToMultiByte(CP_UTF8, ...) for the mirror-image direction).
- Webcam overlays could render as a fully transparent/blank square even
  though the fix in 2.1.0 had frames arriving correctly.
  hr_webcam_capture.cpp copies frames straight out of the source
  reader's RGB32 buffer, but that format's 4th byte per pixel is
  padding, not a real alpha channel, and consumer webcam drivers
  routinely leave it at 0. The overlay compositor's CompositeBgra()
  (hr_overlay_render.cpp) treats every layer's 4th byte as genuine
  per-pixel alpha, so a 0 there made the whole webcam layer invisible
  regardless of what the camera was actually seeing. Capture now forces

  of the reader, before it ever reaches the compositor.
- If the ffmpeg process ended unexpectedly mid-recording (crashed, was

  was actually still alive, so AppState.recording just stayed true

  wall-clock timer that keeps ticking regardless of whether anything's

  or being written, but the UI never said so. PollStats() now detects

[Version 1.7.1] - 2026-07-07

=== Added ===
- `rm --vid` terminal commands - delete recordings straight from the console:
  - `rm --vid #name="..."` - delete one recording by name (extension optional; its companion separate-audio `.mp3` export, if any, is deleted too)
  - `rm --vid @all` - delete every recording in the output folder
  - `rm --vid @last` - delete only the most recently recorded file

- `rm @homrec` (uninstall HomRec) now asks "are you sure?" before doing anything - pass `-q` / `-y` to skip the prompt for scripted use. Previously it ran with no confirmation at all.
- The `!` and `$` command prefixes are now **optional** everywhere in the console. `rm --vid @last` works exactly like `$rm --vid @last`; `create --window ...` works exactly like `!create --window ...`. Old prefixed commands, aliases, rules, and hotkeys keep working unchanged - the prefix is just no longer required.

=== Fixed ===
- Bug 9 (continued) - found the actual remaining source of the CMD flash after confirming it still happened even with `--windowed` set at the PyInstaller level (which rules out the app's own subsystem console - that part was already correct). The real cause: `hr_app_logic.cpp`'s GPU-encoder probe (`hr_probe_gpu_encoder`, run automatically ~3s after every launch to detect NVENC/AMF/QSV support) and its audio/video merge helper (`merge_audio_video`) both used plain `system()` to run ffmpeg. On Windows, `system()` always spawns via a new `cmd.exe`, and unlike `CreateProcess` it has no way to pass `CREATE_NO_WINDOW`/`SW_HIDE` - redirecting the command's own output (`>nul 2>&1`) does nothing to hide the window `system()` itself creates. Replaced both call sites with a hidden `CreateProcess`-based helper (matching the pattern already used correctly elsewhere in the same file, e.g. `hr_launch_ffmpeg`). Requires rebuilding `hr_app_logic.dll`.
- Version number was inconsistent across the app: `homrec.py` still reported `v1.7.0` in five places (title bar, About label, startup log line, taskbar app ID, `CURRENT_VERSION`) despite this actually being `1.7.1`, and the README badge still said `1.6.4`. All bumped to `1.7.1`.
- Removed dead code: `homrec.py`'s preview capture loop tried to import a `CppPipeline` class from `homrec_native.py` for a DXGI fast-path that was never actually implemented there - the import always failed and it silently fell back to the normal path every time anyway. Removed the broken import/init code and the now-fully-unreachable `_capture_loop_cpp` method rather than leave code referencing a class that doesn't exist.
- `$do --ui@homrec 1` (re-download/reinstall `homrec.py` from GitHub) used to write the downloaded file straight over the running app's source with no integrity check at all. It now verifies the download's SHA-256 against a `homrec.py.sha256` published alongside it before writing anything, and aborts (nothing on disk touched) if that checksum is missing or doesn't match - pass `--force` to skip verification if you understand the risk.
- Bug 9 - a CMD/console window could flash up when launching HomRec (double-clicking the .exe, a shortcut, `python homrec.py` with no parent terminal, etc). This was the app's own auto-created console, not one of the ffmpeg/helper subprocesses (those were already silenced - see Bug 2 in 1.7.0). HomRec now detects and hides that auto-created console on startup, while leaving a developer's own already-open terminal alone if they're running it from source to watch log output. Set `HOMREC_SHOW_CONSOLE=1` to opt out.
  - Follow-up fix: the first version of this checked how many processes were attached to the console and only hid it if exactly one was - which broke for PyInstaller builds of `hr.exe`, since a PyInstaller onefile .exe's bootloader stub and the actual unpacked program both attach to the *same* auto-created console, so the count was always 2+ and it never got hidden (this is what people were still seeing after building with PyInstaller). Now checks the actual name of the immediate parent process instead, and only leaves the console alone if it's a real interactive shell (cmd.exe / powershell.exe / pwsh.exe / Windows Terminal).
- Bug 6 - webcam overlay never showed up, in Settings or in the recorded video: the DirectShow device-name probe filtered for the text `(video)`, which never actually appears in FFmpeg's real device listing, so it always fell back to the fake name `"Integrated Webcam"` - a name that doesn't match most people's actual camera, so FFmpeg silently failed to grab it. The probe now correctly parses FFmpeg's `-list_devices` output.
- Bug 7 - webcam overlay preview was always a static placeholder box, both in the Overlays settings editor and in the live preview while recording: it never actually grabbed a frame from the camera. It now shows a real, live feed from the selected camera (falling back to a "no signal" placeholder only if the camera can't be opened).
- Bug 8 - screen preview freezes while recording: the recording-preview path called `resize_nearest_np`, a method that didn't exist anywhere in `homrec_native.py` (only `resize_bilinear_np` did). Every throttled preview update during recording silently threw `AttributeError`, so the preview queue never refilled and the on-screen preview froze on the last frame for the rest of the recording. Added the missing method.
- `requirements.txt` had a leftover, unresolved merge-conflict marker (`=======`) that broke `pip install -r requirements.txt`; cleaned up and de-duplicated (also added `opencv-python` / `numpy`, which the code already depends on but which were missing from the top of the file).

[Version 1.5.0] - 2026-05-29

=== Added ===

Native C/C++ performance extensions (homrec_core, hr_encoder_helpers,
hr_preview, hr_ringbuf, hr_framequeue, hr_stopwatch, hr_display_info,
hr_dxgi_capture, hr_pipeline) - compiled as .dll/.so, loaded at runtime
via ctypes. Auto-discovered next to homrec.py - no config needed.
Graceful fallback to pure Python if any module is missing.

hr_pipeline: unified C++ capture thread - DXGI Desktop Duplication →
BGRA→YUV420p → named pipe (FFmpeg reads) + preview thumbnail.
Eliminates Python-side mss.grab() loop entirely on Windows.

hr_stopwatch: sub-millisecond frame-pacing timer using
QueryPerformanceCounter (Windows) / clock_gettime CLOCK_MONOTONIC (POSIX).
Fixes the 15 ms sleep granularity jitter on Windows that caused frame drops.

hr_dxgi_capture: GPU-accelerated screen capture via DXGI Desktop
Duplication API. Captures frames the moment the compositor presents them
(~1 display cycle latency vs 1-2 frame lag with GDI/BitBlt).

hr_display_info: fast monitor enumeration with per-monitor DPI via
GetDpiForMonitor (Windows) / xrandr (Linux).

homrec_native.py: Python ctypes wrapper for all native libraries with
full Python fallbacks for every function.

"Disable Preview" option in Settings → Advanced → Performance.
Shows a placeholder screen instead of live preview - saves CPU during
recording on low-end hardware.

"Update" button appears in corner when new version is detected
Welcome window shown on first launch

=== Changed ===

Capture loop: preview thread now skips mss.grab() entirely during
recording - no GDI bandwidth competition with FFmpeg.

Codec pipeline: QP range clamped (min qp=23) to prevent near-lossless
encoding (~150 Mbit/s) that saturated weak GPU encoders.

QSV encoder: removed -async_depth 1 which blocked the capture thread
waiting for GPU acknowledgement on each frame, halving FPS on i3/i5.

QSV encoder on UHD Graphics: added -low_power 1 (VDENC fixed-function
path, 2-3× faster than shader PAK) and -look_ahead 0 (removes CPU-side
lookahead overhead).

CPU encoder (libx264): thread count now set to 1 on systems with ≤4
logical cores, avoiding competition with FFmpeg for CPU time.

GIL switch interval raised from 5 ms to 20 ms - reduces GIL contention
between capture, audio and UI threads on weak CPUs. One GIL switch per
frame at 60 FPS instead of three.

OpenCV thread count set to 1 on systems with ≤4 logical cores - preview
resize does not need multiple threads.

gdigrab input: thread_queue_size reduced from 512 to 128, added
-rtbufsize 16M to limit memory pressure on systems with shared CPU+GPU RAM.

Preview update interval during recording raised from 1000 ms to 2000 ms -
capture thread sleeps 500 ms anyway so polling faster was pointless.

Audio recording stop: non-blocking teardown - streams closed before
joining threads so read() unblocks immediately. Eliminates the previous
30-second hang on stop.

=== Fixed ===

hr_audio_rms: int32_t accumulator replaced with int64_t - prevented
integer overflow on buffers larger than ~2M samples.

hr_blend_rgba: alpha compositing rounding bias corrected from +127 to
+128, fixing a systematic 1-LSB error in badge/watermark blending.

hr_framequeue: push() race condition - slot is now written before head
is advanced so the consumer can never observe a null pointer.

hr_framequeue: size() used mismatched memory orders (acquire/relaxed),
now both acquire for correct cross-thread visibility.

hr_ringbuf: wrap-around memcpy off-by-one at exact power-of-2 boundaries
fixed by computing `first` from mask(h) rather than raw cursor.

hr_ringbuf: reset() now zeroes buffer contents - prevents stale PCM data
from a previous recording being read after reset.

hr_display_info: missing #include <algorithm> caused std::stable_sort
to be invisible under MinGW, producing a build error.

hr_encoder_helpers: hr_memcpy_nt now uses _mm_stream_si128 (real NT
stores) instead of _mm_storeu_si128 (cached stores) - the function
previously claimed to be non-temporal but was not.

hr_encoder_helpers: BGRA→YUV420p and RGB→YUV420p chroma now averages
all four luma pixels in each 2×2 block instead of sampling only the
top-left pixel - visibly reduces chroma blur on fine detail.

hr_preview: `restrict` keyword replaced with HR_RESTRICT macro - `restrict`
is C99-only and caused a cascade of "not declared in this scope" errors
when compiled as C++ under MinGW g++.

homrec_native.py: duplicate _DxgiCaptureAPI singleton at module level
removed - dxcap was created twice, second instance silently overwrote
the first.

homrec_native.py: preview thumbnail now uses ctypes data_as() instead
of .tobytes() - eliminates a full buffer copy on every preview frame.

Quality loaded from old settings.json is now clamped to 50–100% to
prevent a saved value of 95–100 (quality=100 → qp=18 → ~150 Mbit/s)
from saturating the encoder on first launch after upgrade.

Application freeze after stopping recording
General optimization improvements
Tray icon logo visibility improved on dark/light taskbars
