[Version 2.2 beta] - 2026-09-12

=== Added ===

- Custom action hotkeys. Settings > Hotkeys now has a "Custom Hotkeys"
  section: add any number of rows, each binding a global hotkey to an
  action string - exactly what you'd type into the console or put in a
  .cfg file (a built-in command, a "setting = value" assignment like
  "disable_preview = true", or anything a plugin registered via
  homrec.register_command()/register_setting()). Coexists with the four
  fixed hotkeys (Start/Stop, Pause, Fullscreen, Save Replay). Persisted
  in homrec.hrc as a new [custom_hotkeys] section, same pattern
  [overlays] already used.
- 10 new Lua plugins in Hom/plugins/ (source in <id>-src/, packaged as
  <id>.hrp, listed in plugins/index.json for `hom install <id>`):
  watermark, rec-info, webhook-notify, soundboard, clip-organizer,
  now-playing, profiles, diag-tools, twitch-info, backup-config. All
  written against the existing homrec.* Lua API (register_command,
  register_setting, settings_get/set, store_get/set, show_toast,
  http_get/post, print/log, and the on_load/on_recording_start/
  on_recording_stop/on_replay_saved hooks) - no new engine-side API
  surface was added to support them.
- Settings > Video & Codec: a "Test Recording (5s)" button. Runs a short,
  disposable recording of the selected monitor using whatever codec/
  encoder preset is currently picked in the tab (even if you haven't hit
  Save yet), then deletes the file and shows the results in a popup:
  encoder actually used (after GPU-encoder fallback), resolution,
  average FPS, frames captured/dropped, and a plain-language verdict on
  whether the machine kept up. Lets you sanity-check a codec/hardware
  encoder before committing to a real recording. Uses its own capture
  pipeline/ffmpeg process (never the real recording's), so it can't be
  confused with an actual recording elsewhere in the app; briefly pauses
  the live preview for the 5 seconds if it's running (DXGI only allows
  one capture handle per monitor at a time) and restores it automatically
  afterward.

=== Fixed ===

- Build: src/hr_hotkey.cpp used std::vector (for the new Custom Hotkeys
  storage above) without including <vector>, so it failed to compile on
  its own (everything depending on HotkeyCtx::customs cascaded into
  further errors right behind it). Added the missing #include <vector>.
- Recordings could finish several times shorter than the actual time
  spent recording (e.g. a 44s take saved as an 11s file) on hardware too
  weak to sustain the requested resolution/fps. The pipeline's rawvideo
  pipe to ffmpeg has no per-frame timestamps - the muxed duration is
  just frame_count/declared_fps - and the existing catch-up mechanism
  meant to compensate for a falling-behind encoder was defeated by the
  same MAX_QUEUE_SIZE backpressure it was supposed to work around: its
  duplicate "catch-up" frames got evicted from the queue just as fast as
  the live ones whenever the writer genuinely couldn't keep up, so they
  never actually reached ffmpeg. Catch-up reps now bypass that backpressure
  cap instead of being dropped, so a chronically overloaded recording
  takes longer to finalize after Stop rather than silently losing
  timeline length.
- h264_amf recordings could come out visibly washed-out/faded compared
  to the same recording with libx264. The app's own BGRA->YUV conversion
  (hr_encoder_helpers.c) produces full-range (PC, 0-255) BT.601 data, but
  nothing ever told ffmpeg/the encoder that, so decoders had to guess -
  libx264's output happened to look right by luck of default player
  behavior, but h264_amf's own range signaling made the mismatch visible.
  hr_ffmpeg_runner.cpp now explicitly declares
  "-color_range pc -colorspace smpte170m -color_primaries smpte170m
  -color_trc smpte170m" so both encoders are told the truth instead of
  guessing.
- FFmpeg could fail to launch with a bare "Failed to start the ffmpeg
  process" and no further explanation, on machines where the ffmpeg
  path, output path, or a Windows username anywhere in those paths
  contained non-ASCII characters. _build_cmdline() in
  hr_ffmpeg_runner.cpp converted those std::string (UTF-8) args to
  std::wstring with a plain std::wstring(s.begin(), s.end()), which
  widens each byte 1:1 instead of decoding UTF-8 - correct only for
  pure ASCII input. Any multi-byte UTF-8 sequence came out as garbled
  wide characters, so CreateProcessW either couldn't find the exe or
  choked on a corrupted command line and failed outright.
  _build_cmdline() now decodes every one of these args with
  MultiByteToWideChar(CP_UTF8, ...), matching the conversion already
  used everywhere else in the app (see hr_app_logic.cpp's
  WideCharToMultiByte(CP_UTF8, ...) for the mirror-image direction).
- Webcam overlays could render as a fully transparent/blank square even
  though the fix in 2.1.0 had frames arriving correctly.
  hr_webcam_capture.cpp copies frames straight out of the source
  reader's RGB32 buffer, but that format's 4th byte per pixel is
  padding, not a real alpha channel, and consumer webcam drivers
  routinely leave it at 0. The overlay compositor's CompositeBgra()
  (hr_overlay_render.cpp) treats every layer's 4th byte as genuine
  per-pixel alpha, so a 0 there made the whole webcam layer invisible
  regardless of what the camera was actually seeing. Capture now forces
  that byte to 0xFF (fully opaque) right after each frame is copied out
  of the reader, before it ever reaches the compositor.
- If the ffmpeg process ended unexpectedly mid-recording (crashed, was
  closed externally, hit a fatal encode error, etc.), nothing ever
  noticed: RecordingController::PollStats() never checked whether ffmpeg
  was actually still alive, so AppState.recording just stayed true
  forever. The bottom-left status dot, elapsed-time readout, and
  "Recording"/"Paused" label are all driven off that flag (and off a
  wall-clock timer that keeps ticking regardless of whether anything's
  actually being encoded), so they'd carry on looking like a perfectly
  normal in-progress recording indefinitely - nothing was left running
  or being written, but the UI never said so. PollStats() now detects
  this (hr_ff_is_running() already existed for exactly this, but nothing
  called it) and main_frame.cpp automatically runs the same stop/
  finalize sequence a manual Stop() would, resets the status bar back to
  Ready, and shows a "Recording Interrupted" popup explaining what
  happened - instead of leaving the last few seconds of recording state
  stuck on screen until you noticed and hit Stop yourself.

[Version 2.1.0] - 2026-09-10

=== Fixed ===

- Window capture (File > Select Window to Record / the window picker
  dialog) silently recorded the wrong thing whenever the target window
  lived on a different monitor than Settings > Monitor happened to be
  set to: RecordingController::ResolveCaptureSize() (src/ui/
  recording_controller.cpp) always captured state_.monitor_id's monitor
  first and only tried to crop the window's rect out of *that* frame
  afterwards, so a window on any other monitor had little/no overlap
  with what was actually captured, tripped the "entirely off the
  selected monitor" fallback, and quietly recorded that other monitor's
  full desktop instead - with no error, so it looked like "record just
  this window" simply didn't work. ResolveCaptureSize() now resolves the
  target window first and picks whichever monitor its center point
  falls on, so window capture works regardless of what Settings >
  Monitor is set to; desktop-only recordings are unaffected. Also
  reuses that one window resolve for both the monitor pick and the crop
  rect instead of re-resolving the window a second time.
- Webcam overlays showed as an empty box with nothing in it - even
  though the same camera worked fine in every other app, and even in
  the final recorded video, not just the live preview.
  hr_webcam_capture.cpp created its IMFSourceReader with no attributes
  and then requested RGB32 frames; almost no consumer webcam natively
  streams RGB32 (most do YUY2/NV12/MJPG), so that SetCurrentMediaType
  call silently failed, the capture thread gave up, and
  GetOrRenderWebcam() (hr_overlay_render.cpp) just kept returning
  nothing to composite, forever, with only a single one-time log
  warning to show for it. Now creates the reader with
  MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING enabled, which makes Media
  Foundation insert the color-conversion MFT it needs automatically, so
  the RGB32 request succeeds regardless of the camera's native format.
- Audio Mixer level meters (Microphone/Desktop Audio bars) visibly
  stepped instead of sliding, with a noticeable lag and a peak-hold dot
  that stuck around far too long. They were being redrawn from
  OnStatsTimer's 500ms/2Hz tick even though hr_peak_decay()
  (hr_ui_utils.cpp) is written assuming ~50ms/20Hz calls - at 2Hz the
  peak-hold sat for ~10s instead of ~1s and then fell off in big jumps
  instead of a smooth slide. The meters now run on their own timer,
  decoupled from the stats tick (main_frame.cpp's new
  OnLevelMeterTimer()/RestartLevelMeterTimer()).
- Closing the app (the titlebar X, or File > Exit) could crash with
  HomRec's own "ran into a problem and needs to close" dialog,
  especially when closing shortly after launch. Cause: g_frame
  (main_frame.cpp) was a plain pointer only cleared in
  ~HomRecMainFrame() - which Destroy() merely *schedules*, possibly
  several event-loop turns later - while CheckHomUpdatesAsync()'s
  detached background thread (the startup plugin-update check, which
  can run for up to 15s) reads g_frame with no synchronization at all
  and calls wxQueueEvent(g_frame, ...). Closing while that thread was
  still in flight could queue an event onto a frame that was already
  (or about to be) freed. g_frame is now std::atomic<HomRecMainFrame*>
  and is cleared at the top of OnClose()'s real-close path instead of
  only in the destructor; the hotkey thunks and the update-check
  handler now read it once via .load() instead of check-then-use.
- Clicking Stop froze the entire app - preview included - for up to
  ~30 seconds (occasionally longer with a slow audio mix/merge), and
  any clicks/drags made during that freeze only visibly landed the
  moment it ended, which read as "it fixes itself after ~30 seconds".
  Cause: DoStop() (main_frame.cpp) called RecordingController::Stop()
  synchronously on the UI thread, and Stop() itself blocked on
  hr_ff_wait()'s up-to-30s ffmpeg-finalize budget plus audio mixing/
  merging - none of which pumped window messages in the meantime, so
  Windows just queued input until the thread came back. That slow tail
  now runs on a background thread (RecordingController::StopAsync(),
  used in place of the old blocking Stop() from DoStop() only - other
  callers like closing the app while recording still use the
  synchronous Stop(), which now just waits for that same background
  thread instead of duplicating the work); state_.recording stays true
  for the whole tail so a second Stop click or a Start click issued
  before it's done is correctly ignored instead of racing pipeline_/
  ffproc_ teardown, and the Start/Stop button is disabled for the same
  window. DoStop()'s post-stop UI work (button reset, the "recording
  saved" summary popup) moved to a new OnRecordingFinalized(), invoked
  via CallAfter once the background thread finishes.

=== Added ===

- File > "Set Preset..." - a small profile manager for .hrc config
  files (src/ui/preset_dialog.h/.cpp), built on the existing HrcConfig
  Save()/Load() Export/Import Settings already used. Presets live in a
  new "presets\" folder next to the exe; the app's own auto-managed
  config is always listed first as the "main config" and can't be
  removed, matching the previous default of just having homrec.hrc.
  From the dialog you can: switch to a preset (loads it and re-saves it
  as the active config, so the switch survives a restart); save the
  current in-session settings as a new named preset; add an existing
  .hrc file (copies it into presets\); or remove one. Overlay-only .hrc
  files (e.g. a copy of the auto-saved homrec_overlays.hrc) work fine as
  presets too - HrcConfig::Load() only touches whichever fields are
  actually present in a file, so one of those just layers its overlay
  list on top of whatever else is currently loaded instead of
  overwriting every other setting; the dialog labels these "Overlays
  only" vs "Full config" in its list.
- Settings > Audio > "Level meter refresh rate (Hz)" (AppState::
  level_meter_fps, 10-60, default 30) - controls the new VU-meter timer
  above; takes effect immediately on Save, and round-trips through
  .hrc profiles and homrec_settings.json like the rest of the Audio
  tab's fields (hr_settings_registry.cpp).

[Version 2.0.3] - 2026-09-04

=== Added ===

- Webcam overlays are now actually baked into recordings, not just shown
  positioned in the live preview. New src/hr_webcam_capture.h/.cpp opens
  the configured device via Media Foundation (IMFSourceReader -- chosen
  over DirectShow's ISampleGrabber/qedit.dll, which Microsoft deprecated
  and which isn't reliably registered on modern 64-bit Windows) and reads
  frames on a dedicated background thread; hr_overlay_render.cpp's new
  GetOrRenderWebcam() composites whatever's most recent every frame, the
  same "always latest, never queued" contract hr_dxgi_capture.cpp already
  uses for screen capture. Previously this overlay type only logged a
  one-time "not baked into recordings yet" warning and produced nothing.
- "Add overlay..." now offers a GIF option alongside Text/Image/Webcam/
  External Overlay. Unlike a static Image overlay, a GIF overlay is
  actually animated in both the live preview and the recording: every
  frame is decoded up front (WIC), each frame's disposal method/position/
  delay from the file's own metadata is resolved once at load time, and
  playback picks whichever frame is due based on wall-clock time - so a
  looping GIF plays at its authored speed regardless of how often the
  capture pipeline composites a frame (src/hr_overlay_render.h/.cpp,
  src/ui/overlays_dock_panel.cpp/.h, src/ui/app_state.h). Adding one works
  the same way Image does - pick a .gif, drag/resize it on the preview
  like any other overlay.
- Installer: an opt-in "Associate .hrc and .hrp files with HomRec" task
  (off by default, alongside the existing desktop-shortcut/autostart
  toggles) that registers both extensions (as ProgIDs HomRec.Profile /
  HomRec.Plugin - same names src/hr_app_logic.cpp's own
  hr_register_file_types() uses, so the two mechanisms can't disagree
  about what a given extension is registered as) and gives them their own
  icons (icons\files_icons\hrc.ico / hrp.ico) instead of Explorer's
  generic file icon (installer/HomRec.iss). hr_register_file_types() also
  gained a .hrp entry (it previously only covered .hrc/.hrl) for the same
  reason.
- Installer: its own icon (icons\hrsetup.ico) instead of reusing hr.exe's
  main.ico, so HomRec-Setup-*.exe doesn't look like a second copy of the
  app itself in Explorer/Downloads while it's running.

=== Fixed ===

- Console: running a command whose output overflowed the visible area
  left the terminal scrolled wherever it happened to be instead of
  following the new output, unlike every other terminal. ConsoleWindow::
  Print() now explicitly scrolls to the caret after inserting text
  (EM_SCROLLCARET) - ES_AUTOVSCROLL alone only covers text typed directly
  into the control, not text inserted programmatically the way every
  command echo/response is (src/ui/console_window.cpp).

=== Changed ===

- Version bumped to 2.0.3 (src/ui/version.h, installer/HomRec.iss).
- Makefile: links -lmfplat -lmfreadwrite -lmf -lmfuuid (Media Foundation,
  for the webcam capture above) and builds src/hr_webcam_capture.cpp.

[Version 2.0.2] - 2026-08-31

Cleanup + small performance/quality-of-life release: no behavior change
for anything that was actually reachable before, aside from the console
prompt and two new console commands.

=== Removed ===

- Eight source files that were never part of either build (Makefile's
  OBJS or CMakeLists.txt's HR_SOURCES) and weren't loaded dynamically by
  anything either - leftovers from the 1.x Python/ctypes-DLL era and one
  never-finished staging design, all confirmed dead via a full grep for
  their exported symbols across the tree before deletion:
    - src/hr_version.cpp - duplicated the version banner as its own
      dllexport'd constants; superseded by src/ui/version.h +
      hr_app_logic.cpp's hr_version_string()/hr_version_gt().
    - src/hr_console.cpp / src/hr_console_pipe_server.cpp - the old
      Python-bridge console DLL design (forward_to_python() and a
      Named Pipe IPC server for it), both explicitly marked
      "NOT CURRENTLY BUILT"; superseded by src/ui/console_window.cpp,
      the console actually compiled into hr.exe today.
    - src/hr_framequeue.cpp, src/hr_ringbuf.cpp, src/hr_preview.cpp,
      src/homrec_core.c - native ctypes extensions from 1.5.0/1.6.0's
      Python UI (see that entry below). 2.0's C++ rewrite ported the
      pieces still needed (hr_stopwatch, hr_display_info, hr_dxgi_capture,
      hr_pipeline, hr_encoder_helpers - all still compiled today) but
      these four never got a native call site and were left behind.
  No header files existed for any of these (none were `#include`d
  anywhere), so nothing else needed touching.

=== Performance ===

- BGRA->YUV420p (hr_bgra_to_yuv420p_band in hr_encoder_helpers.c) - the
  function actually called every captured frame during recording, on
  every worker thread in hr_pipeline.cpp's Yuv420pWorkerPool - along with
  RGB->YUV420p and YUV420p->RGB (used for the live preview thumbnail),
  used to recompute `y*width`, `y1*width`, and `(y/2)*(width/2)` as a
  fresh multiply for every single pixel just to find the row it was
  writing/reading. Hoisted into per-row base pointers computed once per
  row instead, so the inner per-pixel loop is now pure pointer indexing.
  Pixel math and output are bit-for-bit identical - this only removes
  redundant address arithmetic.
- Same hoist applied to bgra_to_thumb()/bgra_downscale() in
  hr_pipeline.cpp (the preview-thumbnail box filter and the
  Settings > Resolution downscale step), both also on the per-frame hot
  path during recording.

=== Changed ===

- Version bumped to 2.0.2 (src/ui/version.h).
- tools/homrec_build.py: fully translated to English (prompts, comments,
  error messages - it was previously a mix of English comments and
  Russian-language interactive prompts). .7z is now a normal, always-
  offered archive format in the build menu instead of only appearing
  when a 7z/7za binary already happened to be on PATH at the time the
  script started; picking it on a machine without 7-Zip installed now
  prints a clear "install 7-Zip and try again" message and skips just
  that one archive instead of the option being invisible.
- The in-app developer console's prompt is now styled after a Unix
  user@host:path# prompt - "homrec@1920x1080:60fps# " instead of the
  previous "1920x1080@60fps # " - while keeping the same at-a-glance
  resolution/fps info and the root-style trailing "#" (fitting, since
  this console can run rm/hom update/etc.). Not a literal copy of a real
  shell prompt, just shaped like one.
- welcome_dialog.cpp/.h - removed the first-run wizard's "system options"
  page (desktop shortcut / launch at startup / tray icon toggles). The
  wizard is back to its originally-documented three pages (greeting ->
  basic settings -> finish); those three toggles are still available
  in Settings > System, and now also as install-time Tasks in the new
  Windows installer.

=== Added ===

- Two new console built-ins, in the same spirit as the existing
  Linux-shell-style command set (ls/rm/env/alias/history/echo/clear):
  `pwd` (prints the folder HomRec resolves its cfg/plugins/log/settings
  paths from) and `whoami` (prints the console/build version string).
  Neither reads or writes anything sensitive, so neither needs the
  "inwid" confirmation gate.
- Windows installer (installer/HomRec.iss, Inno Setup) - per-user install
  (no admin/UAC needed, matches HomRec's next-to-the-exe settings/logs),
  Start Menu + optional desktop shortcut, optional "launch at Windows
  startup" task, and a real uninstaller that asks once before deleting
  homrec.hrc/logs (recordings are never touched). See installer/README.md.
- src/hr_update.cpp / hr_update.h - a real, buildable GitHub-releases
  update checker + self-updater, replacing the old "NOT CURRENTLY BUILT"
  staging file of the same name (which also had a stale hardcoded "1.6.1"
  instead of reading version.h). Wired up to Help > Check for Updates
  (main_frame.cpp's new OnCheckForUpdates()), which - it turns out - had
  a menu item and a translated label ("check_updates") but no handler at
  all; clicking it silently did nothing. Finding an update now offers to
  download and silently launch the new installer, closing the app for it.
- tools/homrec_build.py: optional "build the installer" step (finds
  ISCC.exe, builds installer/HomRec.iss with the release version, drops
  the result in dist\ alongside the archives) and a reminder to attach
  the installer exe - not just the archives - to the GitHub release, or
  auto-update has nothing to find.

[Version 2.0.1] - 2026-08-30

Bug fixes and hardening, no feature changes.

=== Fixed ===

- Pipeline shutdown ("did not stop in time" in the log on basically every
  close/Stop(), plus preview-off-then-Start-Recording intermittently
  failing with "capture pipeline didn't start" until the app was
  restarted): hr_pl_destroy()/hr_pl_stop() detected whether the writer/
  capture threads had actually finished via
  WaitForSingleObject(HANDLE(std::thread::native_handle()), 1000) - only
  correct if std::thread is backed by real Win32 threads. This project
  links -lpthread (the Makefile's posix-threads MinGW model), where
  native_handle() returns a pthread_t rather than a HANDLE, so that check
  never worked: every shutdown "timed out" and detached even though the
  real thread had already exited, which meant finish_thread()'s actual
  cleanup (dx_destroy() releasing the DXGI desktop-duplication interface,
  freeing the Pipeline) silently never ran. Since DXGI only allows one
  duplication interface per output per process, that leaked interface is
  what made a later capture pipeline in the same process fail to start.
  Replaced with a portable std::condition_variable-based completion
  signal each thread sets right before returning (hr_pipeline.cpp).
- hom.exe had no crash handler at all - an unhandled exception surfaced
  only as a bare NT status code (e.g. "hom: exited with code
  3221225477"/0xC0000005) with no way to tell where or why. Added a
  minidump-writing SEH filter (writes to crashes\ next to hom.exe, same
  folder hr.exe already uses) so a future crash is diagnosable instead of
  silent (tools/hom/hom.cpp).
- hom.exe was linked dynamically against libstdc++/libgcc, unlike hr.exe
  - on a machine without the matching MinGW runtime DLLs in PATH,
  hom.exe could fail to run at all. Now built with
  -static-libgcc -static-libstdc++, same as hr.exe (Makefile).
- `hom install`/`hom remove` didn't validate the plugin name at all - a
  crafted name containing "..", a path separator, or a drive letter
  could resolve outside .\plugins\. Rejected up front now
  (tools/hom/hom.cpp).
- The in-app console's `hom` command ran hom.exe synchronously on the
  same thread the whole app's UI is pumped on, so any slow/stalled
  network request (hom does real HTTPS installs/updates) froze all of
  HomRec, not just the console, for up to its own 30s timeout. hom.exe
  now runs on a background thread; the console prints its output once
  it's done (src/ui/console_window.cpp/.h).
- Console output printed one line at a time with no redraw batching, so
  a command producing many lines at once (a `hom` run with a lot of
  output, in particular) was visibly choppy. Batched with
  WM_SETREDRAW around the whole burst (src/ui/console_window.cpp).
- Audio Mixer volume sliders changed the mic/system-audio gain as one
  flat multiplier for the whole ~10ms buffer chunk being processed when
  the slider moved, heard as a choppy, stepped volume change rather than
  a smooth one. Now ramped linearly across the samples in that chunk
  instead - same per-sample cost as before (hr_audio.cpp), no extra CPU
  to speak of.

=== Changed ===

- Version bumped to 2.0.1 (src/ui/version.h).

[Version 2.0] - 2026-08-08

This release rewrites the app from the ground up: HomRec 1.7.2 was a
Python/wxPython UI (src/homrec_app/*) driving a small C++ helper DLL for
capture/encode. 2.0 replaces that entire UI layer with a native C++17 +
wxWidgets app (src/win_main.cpp, src/ui/*) - there is no Python left in
the shipped app, and the old Python-side files (homrec.py, homrec_app/,
homrec_native.py, hr_console_bridge.py, hr_plugin_engine.py,
requirements.txt) are gone. Because of that, this entry summarizes the
rewrite by subsystem instead of as a commit-by-commit diff - a lot of
1.7.2 logic was ported and restructured rather than "changed" in the
usual sense.

=== Added ===

- New native UI (src/ui/): main_frame, settings_dialog,
  advanced_settings_dialog, audio_panel, overlays_dock_panel,
  overlay_placement_dialog, overlay_add_dialogs, welcome_dialog,
  window_picker_dialog, hide_window_dialog, log_viewer_dialog,
  pc_analytics_dialog, console_window, custom_messagebox, theme/
  themed_widgets/win32_theme, language, hrc_config, recording_controller
  - all new, replacing the old wxPython dialogs of the same names.
- Lua plugin system (src/plugins/lua_engine.cpp, lua_api.cpp): plugins
  are loaded from plugin.json + Lua scripts, with a homrec.* API
  (toasts/storage/HTTP/theme colors/input-overlay registration,
  homrec.register_command()/homrec.print() for adding console commands,
  homrec.plugin_info() exposing id/name/version/author). plugin.json
  supports an optional "author" field.
- `hom` plugin package manager (tools/hom/hom.cpp, built separately as
  hom.exe): installs/updates .hrp plugin packages from the Hom/ repo
  folder over HTTPS, with `hom ping` (repo connectivity check) and
  `hom install update-hrp` (reinstalls every already-installed .hrp in
  .\plugins).
- Input overlay system (hr_input_overlay.cpp/.h,
  hr_input_overlay_registry.cpp/.h) with bundled presets
  (plugins/input_overlay_presets/: keyboard qwerty/wasd, mouse, gamepad)
  for showing live key/button presses in recordings.
- New live overlay renderer (hr_overlay_render.cpp/.h) for text/webcam/
  image overlays with position/size/opacity, replacing the old
  Python-side overlay handling.
- Crash handler (hr_crash_handler.cpp/.h), structured logging
  (hr_log.cpp/.h, hr_log_paths.cpp/.h), plugin-specific logging
  (hr_plugin_log.cpp/.h), and basic usage/PC analytics logging
  (hr_pc_log.cpp/.h, surfaced via the new PC analytics dialog).
- hr_system_integration.cpp/.h and hr_archive.cpp/.h (new support
  utilities for OS integration and file archiving respectively).
- Dedicated mic/webcam device enumeration (hr_mic_enum, hr_webcam_enum),

=== Added ===
- `rm --vid` terminal commands - delete recordings straight from the console:
  - `rm --vid #name="..."` - delete one recording by name (extension optional; its companion separate-audio `.mp3` export, if any, is deleted too)

- The `!` and `$` command prefixes are now **optional** everywhere in the console. `rm --vid @last` works exactly like `$rm --vid @last`; `create --window ...` works exactly like `!create --window ...`. Old prefixed commands, aliases, rules, and hotkeys keep working unchanged - the prefix is just no longer required.

=== Fixed ===
- Bug 9 (continued) - found the actual remaining source of the CMD flash after confirming it still happened even with `--windowed` set at the PyInstaller level (which rules out the app's own subsystem console - that part was already correct). The real cause: `hr_app_logic.cpp`'s GPU-encoder probe (`hr_probe_gpu_encoder`, run automatically ~3s after every launch to detect NVENC/AMF/QSV support) and its audio/video merge helper (`merge_audio_video`) both used plain `system()` to run ffmpeg. On Windows, `system()` always spawns via a new `cmd.exe`, and unlike `CreateProcess` it has no way to pass `CREATE_NO_WINDOW`/`SW_HIDE` - redirecting the command's own output (`>nul 2>&1`) does nothing to hide the window `system()` itself creates. Replaced both call sites with a hidden `CreateProcess`-based helper (matching the pattern already used correctly elsewhere in the same file, e.g. `hr_launch_ffmpeg`). Requires rebuilding `hr_app_logic.dll`.
- Version number was inconsistent across the app: `homrec.py` still reported `v1.7.0` in five places (title bar, About label, startup log line, taskbar app ID, `CURRENT_VERSION`) despite this actually being `1.7.1`, and the README badge still said `1.6.4`. All bumped to `1.7.1`.
- Removed dead code: `homrec.py`'s preview capture loop tried to import a `CppPipeline` class from `homrec_native.py` for a DXGI fast-path that was never actually implemented there - the import always failed and it silently fell back to the normal path every time anyway. Removed the broken import/init code and the now-fully-unreachable `_capture_loop_cpp` method rather than leave code referencing a class that doesn't exist.
- `$do --ui@homrec 1` (re-download/reinstall `homrec.py` from GitHub) used to write the downloaded file straight over the running app's source with no integrity check at all. It now verifies the download's SHA-256 against a `homrec.py.sha256` published alongside it before writing anything, and aborts (nothing on disk touched) if that checksum is missing or doesn't match - pass `--force` to skip verification if you understand the risk.
- Bug 9 - a CMD/console window could flash up when launching HomRec (double-clicking the .exe, a shortcut, `python homrec.py` with no parent terminal, etc). This was the app's own auto-created console, not one of the ffmpeg/helper subprocesses (those were already silenced - see Bug 2 in 1.7.0). HomRec now detects and hides that auto-created console on startup, while leaving a developer's own already-open terminal alone if they're running it from source to watch log output. Set `HOMREC_SHOW_CONSOLE=1` to opt out.
  - Follow-up fix: the first version of this checked how many processes were attached to the console and only hid it if exactly one was - which broke for PyInstaller builds of `hr.exe`, since a PyInstaller onefile .exe's bootloader stub and the actual unpacked program both attach to the *same* auto-created console, so the count was always 2+ and it never got hidden (this is what people were still seeing after building with PyInstaller). Now checks the actual name of the immediate parent process instead, and only leaves the console alone if it's a real interactive shell (cmd.exe / powershell.exe / pwsh.exe / Windows Terminal).
- Bug 6 - webcam overlay never showed up, in Settings or in the recorded video: the DirectShow device-name probe filtered for the text `(video)`, which never actually appears in FFmpeg's real device listing, so it always fell back to the fake name `"Integrated Webcam"` - a name that doesn't match most people's actual camera, so FFmpeg silently failed to grab it. The probe now correctly parses FFmpeg's `-list_devices` output.
- Bug 7 - webcam overlay preview was always a static placeholder box, both in the Overlays settings editor and in the live preview while recording: it never actually grabbed a frame from the camera. It now shows a real, live feed from the selected camera (falling back to a "no signal" placeholder only if the camera can't be opened).
- Bug 8 - screen preview freezes while recording: the recording-preview path called `resize_nearest_np`, a method that didn't exist anywhere in `homrec_native.py` (only `resize_bilinear_np` did). Every throttled preview update during recording silently threw `AttributeError`, so the preview queue never refilled and the on-screen preview froze on the last frame for the rest of the recording. Added the missing method.
- `requirements.txt` had a leftover, unresolved merge-conflict marker (`=======`) that broke `pip install -r requirements.txt`; cleaned up and de-duplicated (also added `opencv-python` / `numpy`, which the code already depends on but which were missing from the top of the file).

[Version 1.5.0] - 2026-05-29

=== Added ===

Native C/C++ performance extensions (homrec_core, hr_encoder_helpers,
hr_preview, hr_ringbuf, hr_framequeue, hr_stopwatch, hr_display_info,
hr_dxgi_capture, hr_pipeline) - compiled as .dll/.so, loaded at runtime
via ctypes. Auto-discovered next to homrec.py - no config needed.
Graceful fallback to pure Python if any module is missing.

hr_pipeline: unified C++ capture thread - DXGI Desktop Duplication →
BGRA→YUV420p → named pipe (FFmpeg reads) + preview thumbnail.
Eliminates Python-side mss.grab() loop entirely on Windows.

hr_stopwatch: sub-millisecond frame-pacing timer using
QueryPerformanceCounter (Windows) / clock_gettime CLOCK_MONOTONIC (POSIX).
Fixes the 15 ms sleep granularity jitter on Windows that caused frame drops.

hr_dxgi_capture: GPU-accelerated screen capture via DXGI Desktop
Duplication API. Captures frames the moment the compositor presents them
(~1 display cycle latency vs 1-2 frame lag with GDI/BitBlt).

hr_display_info: fast monitor enumeration with per-monitor DPI via
GetDpiForMonitor (Windows) / xrandr (Linux).

homrec_native.py: Python ctypes wrapper for all native libraries with
full Python fallbacks for every function.

"Disable Preview" option in Settings → Advanced → Performance.
Shows a placeholder screen instead of live preview - saves CPU during
recording on low-end hardware.

"Update" button appears in corner when new version is detected
Welcome window shown on first launch

=== Changed ===

Capture loop: preview thread now skips mss.grab() entirely during
recording - no GDI bandwidth competition with FFmpeg.

Codec pipeline: QP range clamped (min qp=23) to prevent near-lossless
encoding (~150 Mbit/s) that saturated weak GPU encoders.

QSV encoder: removed -async_depth 1 which blocked the capture thread
waiting for GPU acknowledgement on each frame, halving FPS on i3/i5.

QSV encoder on UHD Graphics: added -low_power 1 (VDENC fixed-function
path, 2-3× faster than shader PAK) and -look_ahead 0 (removes CPU-side
lookahead overhead).

CPU encoder (libx264): thread count now set to 1 on systems with ≤4
logical cores, avoiding competition with FFmpeg for CPU time.

GIL switch interval raised from 5 ms to 20 ms - reduces GIL contention
between capture, audio and UI threads on weak CPUs. One GIL switch per
frame at 60 FPS instead of three.

OpenCV thread count set to 1 on systems with ≤4 logical cores - preview
resize does not need multiple threads.

gdigrab input: thread_queue_size reduced from 512 to 128, added
-rtbufsize 16M to limit memory pressure on systems with shared CPU+GPU RAM.

Preview update interval during recording raised from 1000 ms to 2000 ms -
capture thread sleeps 500 ms anyway so polling faster was pointless.

Audio recording stop: non-blocking teardown - streams closed before
joining threads so read() unblocks immediately. Eliminates the previous
30-second hang on stop.

=== Fixed ===

hr_audio_rms: int32_t accumulator replaced with int64_t - prevented
integer overflow on buffers larger than ~2M samples.

hr_blend_rgba: alpha compositing rounding bias corrected from +127 to
+128, fixing a systematic 1-LSB error in badge/watermark blending.

hr_framequeue: push() race condition - slot is now written before head
is advanced so the consumer can never observe a null pointer.

hr_framequeue: size() used mismatched memory orders (acquire/relaxed),
now both acquire for correct cross-thread visibility.

hr_ringbuf: wrap-around memcpy off-by-one at exact power-of-2 boundaries
fixed by computing `first` from mask(h) rather than raw cursor.

hr_ringbuf: reset() now zeroes buffer contents - prevents stale PCM data
from a previous recording being read after reset.

hr_display_info: missing #include <algorithm> caused std::stable_sort
to be invisible under MinGW, producing a build error.

hr_encoder_helpers: hr_memcpy_nt now uses _mm_stream_si128 (real NT
stores) instead of _mm_storeu_si128 (cached stores) - the function
previously claimed to be non-temporal but was not.

hr_encoder_helpers: BGRA→YUV420p and RGB→YUV420p chroma now averages
all four luma pixels in each 2×2 block instead of sampling only the
top-left pixel - visibly reduces chroma blur on fine detail.

hr_preview: `restrict` keyword replaced with HR_RESTRICT macro - `restrict`
is C99-only and caused a cascade of "not declared in this scope" errors
when compiled as C++ under MinGW g++.

homrec_native.py: duplicate _DxgiCaptureAPI singleton at module level
removed - dxcap was created twice, second instance silently overwrote
the first.

homrec_native.py: preview thumbnail now uses ctypes data_as() instead
of .tobytes() - eliminates a full buffer copy on every preview frame.

Quality loaded from old settings.json is now clamped to 50–100% to
prevent a saved value of 95–100 (quality=100 → qp=18 → ~150 Mbit/s)
from saturating the encoder on first launch after upgrade.

Application freeze after stopping recording
General optimization improvements
Tray icon logo visibility improved on dark/light taskbars

Bilinear preview resize: ~4 ms  →  ~0.8 ms   (5× faster)
Audio RMS per chunk:    ~0.15 ms → ~0.04 ms  (3.5× faster)
Badge blend (RGBA):     ~1.2 ms  → ~0.25 ms  (5× faster)
Capture loop latency:   ~30 ms  →  ~12 ms    (2.5× faster)
